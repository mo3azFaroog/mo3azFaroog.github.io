Project Overview

🎫 Ticketing for small teams, without leaving Discord

Many communities and small IT teams already live in Discord, but support requests get lost in chat. This bot gives them a proper ticket workflow inside the server: members open a ticket with a priority, staff triage and assign it, everyone can follow the conversation, and every action is recorded in an audit-log channel.

I built it drawing on my experience on a hospital IT help desk, where the basics (clear priorities, status tracking, ownership and a paper trail) matter more than fancy features.

Features

  • Full ticket lifecycle: create, view, reply, review history and close.
  • Colour-coded embeds: priority (Low, Medium, High, Critical) and status are visible at a glance.
  • Staff tools: change status, assign a ticket to a team member, list and filter tickets, and view statistics.
  • Audit log: new tickets, replies, assignments and status changes are posted to a configurable log channel.
  • Access control: members can only see and reply to their own tickets; staff (Manage Messages) can see all.
  • Multi-server ready: tickets and settings are stored per server, so one bot instance can serve several communities.
  • Safe by default: input validation, length limits, cooldowns and friendly error messages.

How It's Built

Modular structure

The code is a Python package split into focused modules: a bot class, configuration, a data layer, embed helpers and three command groups (cogs) for tickets, staff tools and help.

SQLite data layer

Three tables (tickets, replies, bot_settings) with CHECK constraints on priority and status, foreign keys, and indexes on the common lookups. All queries are parameterised, and every ticket query is scoped to the server it belongs to.

Security and configuration

The Discord token is read from an environment variable (.env), never from the source code, and secrets are excluded from version control.

Quality

The data layer is covered by a pytest suite, linted with Ruff, and checked on every push by a GitHub Actions workflow on Python 3.10 and 3.12.

What I Learned

Moving from a single script to a tested package taught me how much structure matters: separating data access from command handling made the bot easier to test, and a code review of the first version caught real bugs (such as command functions shadowing database helpers) that tests now guard against.
